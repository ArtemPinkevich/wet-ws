## Delta и скрытые требования

Architecture impact: DELTA внутри существующих границ. Application владеет общим autoForward и координирует ручную отправку, Message Flow сохраняет транспортную отправку без истории. Новый небольшой Message UI владеет редактором/адресатом/переключателем и использует App Model; App Shell связывает его. Backend Chat, новый runtime, хранилище и абстракции очередей не нужны.

Protocol delta: Message Flow владеет `message-flow.protocol.ts`: `set-auto-forward {enabled:boolean}` и `send {target:Side,text:string}`, обе с существующими RequestMetadata. Root protocol агрегирует эти команды; Control валидирует unknown до dispatch. Application protocol добавляет обязательный `autoForward:boolean` в snapshot/change. History protocol добавляет `side:'user'` с обязательным target для ручной записи; старые внешние записи сохраняют смысл. Отправитель и получатель обновляются вместе; смешанные версии UI/backend не поддерживаются, при неверном ответе действует существующая resync-механика.

`result ok` подтверждает принятие команды/начало попытки, не доставку приложению получателя. Статус записи отражает callback SendTarget: «Передано на отправку» не подтверждает обработку получателем. Ошибка до попытки — отрицательный result; транспортная ошибка после попытки — статус истории. Нет retries/deduplication по request ID: каждая принятая команда — отдельное действие, UI не переотправляет потерянные команды. Несколько вкладок имеют независимые pending; backend сериализует входящие действия обычным event loop, set задаёт абсолютное значение, последний обработанный set определяет состояние. Порядок ручных/входящих записей — порядок приёма backend, не часы пользователя. Никаких новых обещаний backpressure/лимитов сверх TB-001.

UX delta: переключатель над трафиком, редактор под историей с label, select адресата, явная кнопка; Enter — перенос строки, отправка только кнопкой. Переключатель показывает общее backend-состояние, блокируется до sync/при pending. Редактор доступен без связи; отправка блокируется до sync/готовности адресата/при pending. Ошибки используют существующий alert; status показывает состояние пересылки. Карточки «Вы → Клиент/Сервер» явно отличимы. Узкое окно складывает controls без горизонтального overflow, видимый focus. Визуальная delta двух layout создана до Ready; реализация проверена и принята автором 2026-10-18. Текущие макеты: [wide](../../ui/mockups/main/default.png), [stacked](../../ui/mockups/main/default-stacked.png).

- [B: журнал слева, workspace справа](mockups/main/concept-b-journal.png): выровненные JSON previews облегчают сравнение соседних записей. Минус — направление приходится читать по метке, образ диалога слабее.
- [C: горизонтальная лента над workspace](mockups/main/concept-c-ribbon.png): соседние пакеты видны одновременно, payload получает всю ширину. Минус — меньше строк payload и неудобнее длинная история; для глубокого JSON слабее A/B.

Это три альтернативы, не переключатель режима. Клик по записи выбирает её в workspace; новые события не подменяют выбор, положение чтения или будущий черновик. Разделитель предлагается изменяемым, с минимумом ширины для читаемого preview. До подключения остаётся тот же экран: настройки сторон раскрыты inline, состояния disconnected/waiting раздельны, traffic пуст, workspace предлагает выбрать сообщение. Отдельный welcome/setup не нужен.

Auto-forward ON/OFF должен постоянно отображать подтверждённое глобальное состояние. Выключение forwarding не останавливает наблюдение; остановка прокрутки не меняет передачу. При чтении истории появляется «N новых», возврат к live явный. При потере связи с сервисом состояние неизвестно; старое ON не выдаётся за текущее. Макеты статические, transitions не проверены.

Artificial/user-generated обозначается только в traffic меткой Manual (для готового UI точнее «Создано вручную»), одинаково для созданного и изменённого пакета. Пересылка без изменения такой метки не получает. Цвет стороны сохраняется независимо от происхождения. Будущая отправка использует изменяемого адресата: исходное направление/сохранённый контекст, иначе явный выбор. Будущие действия над конкретным пакетом располагаются у выбора; toolbar всех возможных действий сейчас не добавляется. OFF→ON не должен неявно обещать досылку накопленного: политика требует отдельного решения.

## Мысленная проверка и границы

Короткий text целиком, длинный text — ограниченный preview и перенос строк в workspace; большой JSON — несколько форматированных строк и явное сокращение, полный payload отдельно; глубокий JSON выигрывает от высоты A/B. Binary в будущем требует честного размера и hex preview, без выдуманной JSON-декодировки. Высокая интенсивность: стабильный выбор и scroll anchor, никаких скрытых потерь или агрегации одинаковых сообщений; тысячи записей всё равно потребуют отдельной проверки навигации и производительности. Из картинки нельзя заключить, что поток успевают прочитать. Accessibility, контраст, клавиатура, размеры на реальном мониторе и производительность NOT TESTED.

После выбора композиций сверена canonical architecture: видимых препятствий со стороны App Shell / App Model / Connection UI / Chat UI нет, название Chat UI не диктует визуальную модель. Будущие forwarding-команды, происхождение и отправка требуют самостоятельного согласования поведения/контрактов. Два направления позднее могут получить два управления на месте глобального; несколько клиентов потребуют идентичности источника, но не отдельного экрана на каждого сейчас.

Implementation Ready и остальные продуктовые gates: **NOT RUN**, реализация не входит в поручение. Independent Reviewer до Done неприменим к этой стадии; Done не объявляется. Проверка текущего change set: полный `npm run check` из app — PASS (format:check, lint, typecheck; exit 0). Растровые макеты просмотрены; это визуальная проверка композиции, не работающего интерфейса. [Постановки генерации](mockups/main/generation-prompts.md) сохранены для воспроизводимости намерений; повторная генерация не гарантирует одинакового изображения.
