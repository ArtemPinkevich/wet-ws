# Работа с исходным кодом

Прочитай [инструкции приложения](../AGENTS.md) и [команды сборки](../README.md). Если доступны соседние проектные документы, выбери активную итерацию по [дорожной карте](../../docs/product/roadmap.md) и её Context Pack; не выбирай её только по наибольшему номеру папки.

Перед реализацией свяжи изменение с требованием и способом проверки. Различай согласованные условия и предложения; учитывай явные решения автора в текущем задании. Существование макета не означает выбранный стек или проверенную работу приложения.

В результатах итерации указывай исходный снимок, команды, проверенные артефакты и фактические результаты проверок. Успешная сборка, запуск и обмен — отдельные наблюдения. Краткий итог и ссылку на самостоятельный отчёт, если он нужен, добавляй в Context Pack.

Команды сборки и тестирования фиксируй после выбора технического подхода. Не создавай здесь документацию продукта или дубликаты требований.

Код организуется по реальным ответственностям; технические слои не обязательны. Новая абстракция требует текущего назначения и реального использования. Небольшой wrapper может защищать инвариант или границу зависимости и не является ошибкой сам по себе.

## Сопровождение служебного контракта

Каждое служебное сообщение имеет одного владельца и одно определение. При изменении UI ↔ backend API держи определения рядом с owning backend-feature в `<feature>.protocol.ts`; общий `src/protocol.ts` показывает полный контракт типовым объединением без дублирования payload. Локальные protocol-файлы не импортируют root aggregate, реализации handlers/services, runtime приложения, Node.js/ws/Electron/DOM; типовые зависимости используют import type. Транспорт использует полный контракт, обработчик — локальный. Проверяй unknown-вход до handler, отделяя форму/значения от допустимости по состоянию; отправки и dispatch должны ссылаться на те же определения. Переиспользуй проверки без новой библиотеки/registry по умолчанию. DTO вводи при отдельной семантике, существенном преобразовании или обоснованной независимости внутреннего API; отсутствие DTO нормально. Изменение контракта согласованно обновляет потребителей и поведенческие проверки. Внешний пересылаемый текст не является служебным payload и не нормализуется. Не создавай будущие команды, backend Chat ради UI или дополнительное дерево modules/ без самостоятельного основания.
