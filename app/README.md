# WET-WS

WebSocket-трансивер: независимые подключения клиента и сервера, пересылка новых текстовых сообщений при готовом получателе и общая история в синхронизированных интерфейсах. Принятое без получателя остаётся в истории и автоматически не досылается.

## Сборка и запуск

Рабочий стол: слева локальные именованные заготовки (до 20), в центре редактор, справа чат реального трафика. Ширины областей меняются перетаскиванием или стрелками на разделителе; редактор можно свернуть и восстановить без потери черновика. В узком окне области переключаются кнопками. «Соединения» открывает реальные настройки сервера и приёма клиента.

Открытие сообщения или заготовки создаёт редактируемую копию и не отправляет её. При замене изменённого черновика требуется подтверждение. Кнопки отправки явно показывают адресата; отключение автопересылки не запрещает ручную отправку. Раскрытый JSON — только представление: сохранение и отправка используют исходный текст, включая CR/CRLF в нетронутых участках. Заглушки истории без полного текста нельзя открыть или повторить.

Заготовки хранятся в localStorage профиля/origin; браузерная quota может наступить раньше 20 записей. Повреждение и отказ записи показываются явно, прежние данные молча не очищаются. Черновик и ширины живут до reload. Стабильное хранение между разными адресами/портами Electron пока не гарантируется; импорта/экспорта нет.

Все команды сборки и запуска ниже выполняются из каталога app. Git-корень находится уровнем выше, в wet-ws-ai; Git-команды выполняются оттуда. Требуется Node.js 24.21.0 (см. `.node-version`) и npm. Зависимости закреплены в `package-lock.json`.

```powershell
npm ci
npm run build
npm start
```

Открыть http://127.0.0.1:8080. Остановка сервера — Ctrl+C.

Если в этой рабочей копии сохранён переносимый Node.js, его можно выбрать только для текущего терминала:

```powershell
$env:PATH = (Join-Path $PWD '.tools/node-v24.21.0-win-x64') + ';' + $env:PATH
```

Настольный запуск для разработки — `npm run desktop` после сборки. Windows ZIP создаёт и проверяет `npm run make`; готовые архивы находятся в `out/releases/`. Имя содержит версию, ОС, архитектуру, идентификаторы исходников и SHA256 архива. Для запуска готовой программы распакуйте весь архив и откройте `wet-ws-ai.exe`: отдельный Node.js или браузер не требуется.

## Результаты сборки и очистка

- `out/releases/` — проверенные Windows ZIP и каталоги офлайн-поставки Docker. Старые релизы автоматически не удаляются.
- `out/build/` — отдельный рабочий каталог каждого запуска `npm run make`. После проверки ZIP и сохранения архива с результатом проверки удаляется только каталог этого запуска. При ошибке он остаётся с `failure.json`; предыдущие релизы сохраняются.
- `out/checks/releases/` — краткий результат, SHA256 архива, sourceId и ограничения проверки. Подробные временные скриншоты успешной сборки удаляются вместе с её рабочим каталогом.
- `out/source-snapshots/` и `out/source-manifest.json` — сохранённые исходники и указатель на последний снимок. Снимки и исторические evidence автоматически не удаляются.

После разовой уборки прежние различные сборки сохранены в `out/build/retained/`: их не следует считать текущими релизами. Исторические отчёты сохранены без изменения содержимого; прежний `out/checks-history` находится в `out/checks/history`, прежние каталоги упаковки — в `out/build/retained` с теми же именами. Один полностью побайтно одинаковый распакованный экземпляр удалён.

Обычная компиляция `npm run build` ничего в out не очищает. Офлайн-поставка Docker создаётся командой `npm run make:docker` и хранится в `out/releases/wet-ws-<версия>-linux-amd64-<sourceId>-<runId>/`: `image.tar`, `compose.yaml`, `README.txt`, `SHA256SUMS`. Перед публикацией архив загружается обратно и проверяется запуск с `pull_policy: never` и реальный обмен. Успех удаляет только временные файлы этого запуска, ошибка сохраняет диагностику. Для сборки нужны Docker Engine с Linux-контейнерами и Edge. Для запуска получателю нужны только Docker и Compose v2: из каталога поставки выполните `docker load --input image.tar`, затем `docker compose up -d --pull never`; интерфейс — http://localhost:8080, приём клиента — порт 8081. Интернет для запуска не требуется; сам Docker в комплект не входит. Поставка рассчитана на x64, ARM/эмуляция отдельно не проверены. `npm run make` сейчас поддерживает проверенную Windows x64 поставку и требует установленный Edge. При необходимости `ELECTRON_ZIP_DIR` указывает каталог локального официального ZIP Electron; проверка checksum остаётся включённой. Не запускайте две упаковки одновременно из одной рабочей копии.

## Качество кода

Code-quality tooling должно быть настолько строгим, насколько помогает проекту, но не строже. Автоматизируются однозначные машинные проверки; контекстные и архитектурные суждения остаются в анализе и review.

- **Prettier** — единственный источник истины для механического форматирования; stylistic lint rules его не дублируют.
- **TypeScript compiler** отвечает за языковую и типовую корректность. Strict-подход сохраняется; дополнительный strictness flag требует конкретной практической пользы.
- **ESLint** — deterministic correctness reviewer: ошибки async/await, unsafe propagation, неиспользуемый код и импорты, опасные suppressions и другие объективные ошибки. Правило включается как error либо выключается; допустимой категории warnings нет. Сам any и assertions не запрещаются глобально.

Конкретные настройки, версии, охват файлов и автоматические правила определяются только [package.json](package.json), [package-lock.json](package-lock.json), [Prettier config](.prettierrc.json), [Prettier exclusions](.prettierignore), [ESLint config](eslint.config.mjs) и [tsconfig](tsconfig.json); списки правил здесь не дублируются.

Во время разработки допустимы npm run format, npm run lint:fix и подходящие узкие проверки (lint, typecheck, format:check или отдельные файлы). Они помогают работать локально, но перед завершением **любого change set** обязателен успешный полный canonical gate из app:

```powershell
npm run check
```

Он выполняет format:check → lint → typecheck и ничего не исправляет. Непройденный check не позволяет объявлять работу завершённой. Тесты остаются отдельным verification layer, а не частью check; объединение команд потребует отдельного осознанного решения. Момент выполнения и фиксация результата заданы существующим iteration workflow.

Линтер не задаёт архитектуру и не требует helpers, wrappers или слоёв ради style/size/complexity score. Новая структура нужна только для реальной отдельной ответственности или границы. Направление автоматизации: **architecture → stable repository invariant → automated rule**, а не выбор архитектуры под lint plugin. Автоматизация такой границы — отдельный change set после её стабилизации, не новая зависимость заранее.

CI и pre-commit hooks сейчас отсутствуют. CI вводится отдельной задачей и должен выполнять тот же npm run check без исправлений. Husky/lint-staged и другие hooks допустимы только как решение наблюдаемой проблемы, не обязательный атрибут проекта.

## Проверки

После `npm run build` команда `npm run check:iteration-04` проверяет новый рабочий стол в Edge и реальный WebSocket: редактирование/повтор, локальные заготовки, ошибки/лимит, CR/CRLF, длинный JSON с live traffic, размеры и narrow. `npm run check:iteration-04 -- desktop` запускает Electron из исходников. JSON/скриншоты — `out/checks/iteration-04`; новые ZIP/Docker эти проверки не подтверждают. Прежние `check:iteration-02/03` используют текущие controls; семантика их транспортных проверок сохранена.

```powershell
npm test
npm run check:iteration-02
npm run check:iteration-02 -- desktop
```

Проверка Iteration 3 (`check:iteration-03`) проверяет управляемую пересылку, ручной текст обоим адресатам, два интерфейса, reconnect, черновик и узкий экран. Режим `desktop` этой команды запускает Electron из текущих исходников, не ZIP. JSON и скриншоты — `out/checks/iteration-03`; для отдельного запуска задайте `CHECKS_DIR`. Сначала выполните `npm run build`. Это не подтверждает новую контейнерную/ZIP-поставку.

Проверка Iteration 2 использует установленный Microsoft Edge (`BROWSER_CHANNEL` может выбрать другой канал Chromium). Для режима `desktop` задайте `DESKTOP_EXE` — путь к exe из распакованного ZIP в `out/build/`. Команда `npm run make` делает это автоматически. Проверяются реальный обмен, два интерфейса, reload, общая очистка, независимое отключение и узкий экран. Скриншоты — `out/checks/iteration-02`. Linux-контейнер проверяется отдельно. Решением автора от 2026-10-17 проверка между несколькими физическими компьютерами LAN исключена из обязательных проверок текущих и будущих итераций: такой среды нет. Межмашинная работа остаётся непроверенной; локальные тесты не являются её подтверждением.

## Ручной эхо-стенд

Исходник клиента и эхо-сервера — [echo-demo/server.mjs](echo-demo/server.mjs); Dockerfile и compose.yaml стенда находятся в том же каталоге. Стенд использует зависимость ws из общего package.json приложения.

Через Docker из каталога app:

```powershell
docker compose -f echo-demo/compose.yaml up --build -d
```

Откройте http://127.0.0.1:9001 — это проверочный клиент. В трансивере укажите `ws://127.0.0.1:9000` для сервера, подключите его, затем начните приём клиента на порту 8081. На странице клиента подключитесь к `ws://127.0.0.1:8081`, отправьте текст и получите тот же ответ. Страница работает в браузере; Docker запускает её HTTP-сервис и эхо-сервер. Node.js на компьютере для этого варианта не требуется.

Если сам трансивер работает в Docker Desktop, адрес эхо-сервера в трансивере — `ws://host.docker.internal:9000`: localhost внутри контейнера относится к самому контейнеру. Если клиент открыт на другой машине, укажите адрес компьютера с трансивером вместо 127.0.0.1. Порты 9000/9001 должны быть свободны; этот запуск заменяет `npm run demo:echo`.

Остановка:

```powershell
docker compose -f echo-demo/compose.yaml down
```

Для запуска без Docker:

В отдельном терминале из app:

```powershell
npm run demo:echo
```

Эхо-сервер принимает соединения на порту 9000, простая страница клиента доступна на http://127.0.0.1:9001. В трансивере укажите целевой адрес `ws://127.0.0.1:9000`, подключите сервер и начните приём клиента на порту 8081. На странице клиента укажите показанный трансивером адрес, нажмите «Подключить», затем отправьте текст. Клиент получает тот же текст, история трансивера показывает оба направления. Порядок подключения выбираете сами; при отсутствии получателя автоматической досылки нет.

На другой машине замените 127.0.0.1 адресом компьютера с соответствующим сервисом. UI трансивера по умолчанию доступен по LAN на порту 8080, приём клиента — на выбранном порту (8081 по умолчанию). Оба порта должны быть доступны в firewall; в контейнере их нужно опубликовать. Общий подпротокол можно оставить пустым. Стенд запускается отдельно от продукта; `ECHO_PORT` / `CLIENT_PORT` меняют его порты. Остановка — Ctrl+C.

Для проверок обеих поставок из одного снимка сначала выполните `npm run snapshot`, затем запускайте сборки из созданного каталога `out/source-snapshots/<sourceId>`. `manifest.json` хранит хеши исходников; исходный каталог снимка после создания не редактируется. Устанавливаемые зависимости и артефакты внутри него в исходный манифест не входят.

Статус конкретного запуска смотрите в JSON-отчётах: создание артефакта, запуск и приёмка — отдельные результаты. Облачная/корпоративная эксплуатация и ОС кроме Windows требуют собственных проверок.

## Контейнер

Нужен работающий Docker Engine с Linux-контейнерами:

```powershell
docker build --platform linux/amd64 -t wet-ws-ai:iteration-02 .
docker run --rm --name wet-ws-iteration-02 -p 8080:8080 -p 8081:8081 wet-ws-ai:iteration-02
```

## Структура

- `src/backend` — Application, Connection, Message Flow, History, Control, каждый в собственном каталоге.
- `src/frontend` — App Shell, App Model, Connection UI, Chat UI, Control Client, каждый в собственном каталоге.
- `src/runtime` — связывание реализаций и точки запуска Node.js/Electron.
- `src/protocol.ts` — типовой aggregate служебного API; определения и guards рядом с owning backend-модулями в `*.protocol.ts`.
- `src/shared/contracts.ts` — общие метаданные запросов и небольшие чистые guards.
- `tests/runtime` — HTTP/служебный WS и жизненный цикл сервиса; `tests/integration` — взаимодействие модулей.
- cho-demo — проверочный клиент, эхо-сервер и их Docker-запуск.
- `scripts` — сборка ресурсов, снимки и проверка поставок.
- `dist`, `out`, `node_modules`, `.tools` — локальные генерируемые данные, исключённые из Git.

Продуктовые и проектные документы находятся в соседнем каталоге docs общего репозитория. Они не нужны для выполнения приведённых команд.
